## 2. Design decisions made while building
- **Debate dwell (presentation timing, not state):** real logs record a debate line and the speaker's completion at the same instant, so the bubble vanished in ~60 ms. Playback now waits 4.5 s (1×) / 2.25 s (4×) after a `debate.message` before applying the next stored event. State stays exactly as the log says: the character is "talking" until the next event is applied.
- **Live catch-up:** live events go through the same queue. If more than 8 events are waiting, they are applied at once without walking (`LIVE_CATCH_UP_BACKLOG`). No event is ever dropped or reordered.
- **Bubbles:** speaker prefix and markdown are stripped for the bubble only. The full text stays in the feed and the detail panel.
- **Direct API + CORS:** the browser calls FastAPI directly (`NEXT_PUBLIC_API_BASE`, default `http://localhost:8000`), so SSE is not buffered by a dev proxy. The backend allows only `STOCK_OFFICE_CORS_ORIGINS` (default `http://localhost:3000`) and GET/POST.
- **Floor rendering:** floor tiles are drawn from the Tiled tile layer by our own isometric projection (`office/layout.ts`), not Phaser's tilemap renderer. Spots, zones and furniture positions all use one tested formula.

## 4. Performance (measured, not assumed)
Edge window 1500×860, **Next.js dev build**, 4× replay with characters walking: `actualFps` per second = 60, 60, 59, 59, 48, 44, 48, 51, 53, 55, 56 → **44–60 fps, mean ≈ 54**. Dips happen while several characters walk. The production build was not measured. Target "≈60 fps on desktop": **partly met**.

## 5. Known limitations / next (Sprint 2B)

- No shadcn/ui yet; the Analysis Mode (React Flow) is not built.
- FPS dips while walking (sprite and text depth updates every frame); to optimize in 2B if it persists in a production build.
